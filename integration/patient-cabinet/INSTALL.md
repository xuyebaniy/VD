# Кабинет родителя: email-код и дневники — серверный пакет v2

**Пакет подготовлен, но не подключён к опубликованному демо.** GitHub Pages не выполняет PHP и не отправляет письма. Для настоящей регистрации этот код устанавливают на хостинг клиники и указывают действующий SMTP. Никаких тестовых кодов, фиктивной отправки, публичных ключей или стороннего облачного хранилища в рабочем коде нет.

## Сценарий и ограничения

Новый родитель указывает ФИО, мобильный телефон и почту. Сервер отправляет шестизначный код **только на почту**. После проверки создаётся отдельный аккаунт. При следующем входе достаточно почты и нового кода. Телефон — контактное поле; его принадлежность не подтверждена. Подтверждение почты также не подтверждает личность человека или его полномочия законного представителя.

Родитель добавляет детей по имени; дата рождения необязательна. У каждого ребёнка отдельные ежедневные отметки и рекомендации. Ребёнок не получает отдельный логин. Введённые родителем ФИО/телефон до проверки кода находятся только в зашифрованной записи ожидающего подтверждения; аккаунта ещё нет. Повторная регистрация уже подтверждённой почты открывает существующий кабинет и не заменяет его ФИО, телефон или детей.

Вход врача по SMS **не включён**: соответствующие методы всегда возвращают `DOCTOR_AUTH_UNAVAILABLE`. В базе уже предусмотрены роль врача, прикрепление детей и проверка доступа на каждом запросе. Роль нельзя получить регистрацией на почту, передав поле `role` или совпав с телефонным номером врача. Для настоящего входа врача потребуется отдельная реализация SMS и проверки клиникой; выдачи токенов врача или запасного email-входа сейчас нет.

Медицинские документы, МИС и передача результатов анализов не подключены. Самостоятельно созданный профиль не даёт доступа к медицинской карте. Для межустройственной работы дневника уже требуется эта серверная база; большую архитектуру документов можно подключать позже.

## Установка

1. Нужен PHP **8.1+** с `pdo_sqlite`, `openssl` и `curl`; libcurl должен поддерживать SMTP/SMTPS. SQLite используется для небольшого первого запуска на одном сервере. Для нескольких серверов или существенного роста потребуется миграция в управляемую базу; код не выполняет её автоматически.
2. Создать приватный каталог вне `document root`, например `/home/ACCOUNT/private/vd-cabinet`, с правами `0700`. Скопировать `config.example.php` в приватный `config.php` с правами `0600`. Путь приватного конфига должен быть вне публичного сайта. Заполнить фактические `public_root`, `private_dir`, `allowed_origins`.
3. Сгенерировать секреты **на сервере**, не в публичном репозитории:

   ```sh
   php -r 'echo bin2hex(random_bytes(32)), PHP_EOL;'
   php -r 'echo base64_encode(random_bytes(32)), PHP_EOL;'
   ```

   Первый результат — `secret`, второй — `encryption_key`. Ключи хранить и резервировать отдельно от общедоступных файлов. Изменение ключей без миграции блокирует чтение существующего хранилища. Потеря ключа означает потерю возможности расшифровать данные.
4. Вписать SMTP клиники: `smtp_host`, целочисленный `smtp_port`, `smtp_security`, `smtp_username`, `smtp_password`, `smtp_from`. Отправитель должен быть разрешён почтовым сервисом. Обычно используется `smtps` на 465 или `starttls` на 587 — точные параметры берутся у действующего провайдера. Не нужен новый почтовый сервис, если существующий поддерживает эту отправку. Настройку SPF/DKIM/DMARC выполняет администратор домена по требованиям этого сервиса.
5. Для публичного API установить **только** `patient-cabinet.php`, `Cabinet.php`, `SmtpSender.php`, например в `/local/api/`. Конфиг, `admin.php`, тесты, инструкцию и базу не копировать в web root. CLI-оператору нужна отдельная приватная копия `admin.php`, `Cabinet.php`, `SmtpSender.php`.
6. В окружении PHP/FastCGI задать `VD_CABINET_CONFIG` — абсолютный путь к приватному конфигу. Настроить HTTPS и передачу заголовка `Authorization` в PHP. При внешнем TLS-прокси `HTTPS=on` задаёт доверенная серверная конфигурация; произвольные `X-Forwarded-*` запросов не используются.
7. После проверки параметров установить `enabled => true`. API проверяет строгие права файлов и создаёт `cabinet-v2.sqlite` с WAL в приватном каталоге. ФИО, почта, телефон, даты рождения, дневники, рекомендации и основания прикрепления шифруются AES-256-GCM. Идентификаторы, даты отметок, сроки и связь врач–ребёнок остаются техническими метаданными. Коды и токены хранятся только в виде HMAC.
8. При размещении на выделенном поддомене пример пути готовности: `https://cabinet.vash-doc.ru/local/api/patient-cabinet.php?action=health`. Поддомен в инструкции — пример конфигурации; пакет его не создаёт. API возвращает:

   ```json
   {
     "ready": true,
     "service": "patient-cabinet",
     "apiVersion": 2,
     "auth": {"parent": "email", "doctor": "unavailable"}
   }
   ```

   `ready` проверяет локальную конфигурацию SMTP/TLS, ключи, расширения и базу. Он **не отправляет письма, не проверяет пароль у SMTP и не подтверждает доставку в ящик**. После установки нужен согласованный тест входа на адрес ответственного сотрудника. Успех `request-code` означает, что SMTP принял письмо; доставка в ящик может задержаться или письмо может попасть в спам. Ошибка SMTP не показывает успешную отправку.

## Подключение интерфейса и виджета записи

Реальный интерфейс кабинета и его API следует размещать на одном выделенном HTTPS-origin клиники, например `https://cabinet.vash-doc.ru`, без сторонних скриптов основного сайта. Этот адрес потребуется отдельно настроить на хостинге и в DNS. Endpoint передаётся фронту публичной настройкой, например `/local/api/patient-cabinet.php`; в ней нет секретов. Публичный GitHub Pages пока остаётся демоверсией.

Перед включением настоящих аккаунтов компактный Medihost должен работать **на отдельном origin**: например, публичный `booking-widget.html` на GitHub Pages можно оставить внутри iframe кабинета на origin клиники. Это сохраняет компактный вид записи и отделяет сторонний скрипт от ФИО, дневника и авторизации. Путь в другом каталоге того же домена не является отдельным origin. Нельзя включать настоящий кабинет в текущем демо с тем же origin виджета.

**На приватном origin вообще не должно быть доступной копии `booking-widget.html` или другого загрузчика стороннего виджета.** Недостаточно указать отдельный URL в настройке: иначе сторонний скрипт мог бы открыть локальную копию в дочернем iframe и снова получить доступ к origin кабинета. Поэтому сборка `_site`/`stage_public.py` предназначена только для публичного демо; её нельзя переносить в кабинет, даже с изменённым `cabinet-config.js`.

### Отдельная сборка приватного интерфейса

После сборки проверенного каталога, фотографий и иконок приложения подготовить **новый пустой каталог** командой из корня репозитория:

```sh
python3 scripts/stage_clinic.py \
  --origin https://cabinet.vash-doc.ru \
  --booking-widget https://xuyebaniy.github.io/VD/booking-widget.html \
  --output /tmp/vd-clinic-release
python3 tests/clinic-build.py
```

Это пример локальной подготовки файлов; команда не создаёт поддомен, не развёртывает приложение и не активирует почту. `--origin` должен соответствовать будущему выделенному HTTPS-origin, `--booking-widget` — доверенному публичному URL на другом origin. Выходной каталог должен быть новым или пустым. Сборщик отказывается перезаписывать непустой каталог.

Сборщик копирует только разрешённые UI-файлы, каталог и изображения; генерирует `cabinet-config.js` с `apiUrl: '/local/api/patient-cabinet.php'` только в выходном каталоге. Из копии `sw.js` удаляется локальный booking wrapper; приватный кеш получает отдельную версию. Исходные настройки публичного демо и его Service Worker не меняются. `index.html` — единственный HTML-документ в приватном статическом артефакте. Код API устанавливается отдельно, как описано выше.

Размещать результат нужно в **новом пустом web root выделенного origin**, где раньше не публиковалось демо. Не использовать общий каталог сайта с внешними скриптами, алиасы на `_site`, старый Service Worker или уже закешированный локальный виджет. Не добавлять на этот origin копии провайдерских страниц под другими именами.

Для Apache 2.4 сборка содержит `.htaccess`, запрещающий `booking-widget.html` на любом уровне пути и добавляющий запрет встраивания приватных страниц. Администратор должен убедиться, что `AllowOverride` и нужные модули включены. Nginx не читает `.htaccess`; в его конфигурации нужна эквивалентная блокировка, например:

```nginx
location ~* /booking-widget\.html$ {
    return 404;
}
add_header X-Frame-Options "DENY" always;
add_header Content-Security-Policy "frame-ancestors 'none'" always;
```

Правила должны действовать также при rewrite/alias и для вложенных путей; их порядок проверяет администратор. До приёма реальных данных проверить по HTTPS, что приватный `/booking-widget.html` возвращает **403/404**, не `index.html`, не страницу провайдера и не старый кеш. Проверить отсутствие других копий загрузчика и работу внешнего компактного виджета внутри приложения. `tests/clinic-build.py` проверяет состав локального артефакта и сохранность демо, но не может подтвердить конфигурацию ещё не созданного веб-сервера.

Фронт хранит bearer-токен только в памяти вкладки, не в `localStorage`, `sessionStorage`, URL, cookies или Service Worker. Срок — 30 минут; после перезагрузки страницы понадобится новый вход. Настоящие запросы идут с `credentials: 'omit'`, `Authorization: Bearer ...` и `cache: 'no-store'`. В реальном режиме нельзя автоматически переходить на демоданные при ошибке API. Демонстрация доступна только явным отдельным действием.

Ответы API содержат `Cache-Control: no-store, private`. Исключить весь API из Bitrix/CDN/Service Worker-кеша. Не журналировать тела запросов/ответов, токены, коды и SMTP-переписку в access/error/APM-логах. CORS разрешается только точным HTTPS-origin приложения, без `*`. CORS не заменяет проверку токена и прав.

## Контракт API

Все запросы используют `?action=...`. Тела `POST`/`PUT` — JSON-объекты, максимум 16 KiB. У защищённых действий — bearer в заголовке. Ошибка: HTTP 4xx/5xx и `{"error":{"code":"…","message":"…"},"retryAfter":0}`. При ограничении возвращаются положительный `retryAfter` и заголовок `Retry-After`.

| Метод/action | Вход | Ответ |
| --- | --- | --- |
| GET `health` | — | `ready`, `service`, `apiVersion:2`, `auth` |
| POST `request-code` | `{email,intent:"register",fullName,phone}` либо `{email,intent:"login"}` | `{challengeId,expiresIn,retryAfter,emailMasked}`; кода нет |
| POST `verify-code` | `{challengeId,code}`; код строкой | `{token,expiresAt,account,children}` |
| GET `me` | bearer | `{account,children}` |
| POST `children` | `{name,birthDate?,relationship}` | `{child}`; HTTP 201 |
| GET `garden` | query `childId`, `month=YYYY-MM` | `{garden}` |
| PUT `garden` | query `childId`; `{date,entry}` | `{garden}` соответствующего месяца |
| POST `logout` | `{}` | `{ok:true}` и отзыв токена |
| GET `documents` | query `childId` | Пустой список, `linkStatus:"not_connected"` |
| POST `request-doctor-code` / `verify-doctor-code` | — | HTTP 503, `DOCTOR_AUTH_UNAVAILABLE` |
| GET `doctor-children` | Токен врача после будущего SMS-подключения | Только прикреплённые дети |
| GET `doctor-garden` | query `childId`, `month`; токен врача | Дневник только прикреплённого ребёнка |
| PUT `doctor-recommendations` | query `childId`; `{recommendations:{water:"…",…}}`; токен врача | `{recommendations,updatedAt}` только прикреплённого ребёнка |

`account`: `{id,role:"parent",displayName,emailMasked,phoneMasked,phoneVerified:false}`. `child`: `{id,name,birthDate,relationship,linkStatus:"unverified",doctorIds,doctorAssignment:{status:"assigned"|"unassigned",doctors:[{id,displayName}]}}`.

`garden`: `{entries:{"YYYY-MM-DD":entry},goals:[],updatedAt,recommendations,recommendationsUpdatedAt}`. Пустые `entries`/`recommendations` — JSON-объекты `{}`, не массивы.

Поля `entry`: `meal`, `water`, `activity`, `sleep`, `screen`, `mood`; значения `done`, `partial`, `missed`. `null` снимает отметку, не превращая отсутствие данных в невыполнение. `note` — до 1200 символов, пустая строка удаляет заметку. Частичное сохранение меняет только переданные поля выбранного дня; остальные дни и отметки сохраняются. Будущие дни и дни до указанной даты рождения отклоняются. Календарная зона — Москва. Рекомендации — те же шесть ключей, каждый текст до 1200 символов; пустая строка удаляет пункт. Врач не может изменять родительские отметки.

ФИО родителя — до 150 символов; имя ребёнка — до 100. Телефон — российский мобильный `+7 9…` (начальная `8` нормализуется). Почта в v2 — обычный ASCII-адрес; регистр нормализуется. `relationship`: `mother`, `father`, `grandmother`, `grandfather`, `guardian`.

### Коды, лимиты и ошибки

Код действует 10 минут, допускает 5 неверных попыток. Повторная отправка — через 60 секунд; новый код отзывает прежний. Верификация и выдача сеанса атомарны. Один код нельзя применить повторно. До 5 запросов на почту в час, 10 в сутки, 20 с IP в час; глобальные пределы задаются `email_hour_limit`/`email_day_limit`. Неудачная отправка также учитывается. Успешный новый вход сохраняет максимум три активных сеанса аккаунта.

Ответ `request-code` не раскрывает, существует ли аккаунт. Для неизвестного адреса при `intent:"login"` требование регистрации (`409 REGISTRATION_REQUIRED`) появляется только после верного кода. Фронт переводит человека в форму регистрации. Вход по существующей почте сохраняет прежнюю семью. Письмо содержит только код, без ФИО, телефона, детей и данных дневника.

## Оператор: прикрепление врача

Публичных административных методов нет. Сотрудник клиники использует CLI на сервере после проверки соответствующего основания. Вход — JSON через stdin, чтобы не оставлять персональные сведения в аргументах процесса и истории shell. Секреты передаются только приватным конфигом.

| Команда | JSON | Результат |
| --- | --- | --- |
| `php admin.php children` | `{email}` | Дети указанного подтверждённого родителя; вывод содержит персональные данные |
| `php admin.php provision-doctor` | `{fullName,phone}` | `{doctorId,signInEnabled:false}`; создаёт профиль, не выдаёт вход |
| `php admin.php assign-doctor` | `{doctorId,childId,evidence}` | Прикрепляет ребёнка к врачу; `evidence` — основание/идентификатор проверки сотрудником, до 1000 символов |
| `php admin.php unassign-doctor` | `{doctorId,childId}` | Отзывает прикрепление и сеансы врача |

Клиника отвечает за идентификацию человека, проверку полномочий представителя, основание доступа врача и дальнейшие процедуры хранения/удаления. Это не реализовано простой проверкой почты. Автоматического прикрепления «все пациенты ко всем врачам» нет. Одно и то же ФИО или контактный телефон не объединяет аккаунты или медицинские карты.

## Хранение, резервирование и обновления

База и журнал WAL находятся вне публичного сайта. Резервировать их штатным механизмом SQLite Backup вместе с приватными ключами; копирование только основного `.sqlite` во время записи может дать неполный снимок. Доступ к резервам ограничить. Нужны проверка восстановления, мониторинг диска, лимиты веб-сервера и установленный клиникой порядок удаления данных и аудита перед реальным запуском.

Ожидающие подтверждения и технические попытки старше двух суток очищаются при запросах кодов; просроченные сеансы — там же. Аудит содержит идентификаторы и события, без содержимого писем/дневника. Автоматический срок хранения аккаунтов, медицинской информации или аудита здесь не устанавливается.

Старый прототип v1 имел SMS-вход и другой формат базы. При обнаружении `cabinet.sqlite` рядом v2 останавливается с `MIGRATION_REQUIRED`: не переименовывать старую базу и не пытаться использовать её как v2. Если v1 действительно когда-либо использовался, нужна отдельная миграция с сохранением идентификаторов и ключей. Демоданные браузера автоматически не загружаются на сервер.

## Проверки

```sh
php tests/security.php
python3 tests/http_security.py php
```

Первая проверка использует только тестовые подклассы отправителя и временное хранилище. Вторая запускает реальный PHP-router на loopback и проверяет HTTP-контракт, авторизацию, семейную изоляцию и HTTP-заголовки. Настоящие письма/SMS не отправляются; боевой код не содержит тестового OTP или переключателя обхода. Папку `tests` никогда не устанавливать в web root. GitHub Pages-сборка по явному списку не включает этот серверный каталог.

SMTP-реализация опирается на документированные [SMTP-возможности libcurl](https://curl.se/libcurl/c/smtp-tls.html) и [обязательный режим TLS `CURLUSESSL_ALL`](https://curl.se/libcurl/c/CURLOPT_USE_SSL.html). Сертификат и имя сервера проверяются; отключать эти проверки для «починки» подключения нельзя.
